# Отчёт по индивидуальному заданию № 2

Разработка многопоточной имитационной программы («Архитектура компьютера и операционные системы»)

## 1. Автор

Хингелов Глеб Владимирович, группа БПИ252.

## 2. Вариант и условие

Задание № 2 — многопоточная имитация. Предметная область та же, что в ДЗ № 1: морской бой двух игроков под управлением судьи. Судья хранит оба поля и сообщает результат выстрела, игроки поля врага не видят. Теперь судья и каждый игрок — отдельные потоки pthread.

## 3. Сценарий: сущности и потоки

| Сущность | Реализация | Почему |
|---|---|---|
| Судья | главный поток (Fight в judge.c) | есть поведение: расставляет флоты, даёт ход, применяет выстрел, проверяет правила, пишет ход |
| Игрок «Нельсон» | поток PlayerThread | есть поведение: выбирает клетку по своей стратегии и запоминает ответ судьи |
| Игрок «Ушаков» | поток PlayerThread | то же |
| Поле, корабль | структуры данных (не потоки) | своего поведения не имеют, это данные судьи |

Итого 3 потока. Взаимодействие: на каждого игрока три семафора и общая структура Seat.

```
судья:  sem_post(turn) → sem_wait(shot) → применить выстрел → записать r → sem_post(reply)
игрок:  sem_wait(turn) → выбрать (x,y)  → sem_post(shot)   → sem_wait(reply) → запомнить ответ
```

- **turn** — «твой ход» (судья → игрок); **shot** — «клетка выбрана» (игрок → судья); **reply** — «результат готов» (судья → игрок).
- Мьютекс `s_out` защищает вывод (экран и журнал): игрок печатает «целится в …», судья — результат хода, строки не перемешиваются.
- В каждый момент работает только игрок, у которого ход; семафоры гарантируют, что данные в Seat (x, y, r) не читаются и не пишутся одновременно, поэтому бой остаётся воспроизводимым по seed.
- Конец боя: судья ставит флаг `over` (атомарный) и делает `sem_post` обоих семафоров, потоки выходят, затем `pthread_join`.

## 4. Пользовательский интерфейс

Консольный. Каждый ход — две строки: что выбрал игрок и что сообщил судья («мимо / ПОПАЛ / УБИЛ»). В конце печатаются оба поля с кораблями, победитель и статистика (выстрелы, попадания, убитые корабли). Всё дублируется в журнал `battleship.log` (ввод-вывод через `open`/`dprintf`). Задержка между ходами задаётся параметром `delay`.

## 5. Запуск и завершение

```
mkdir -p build && cd build && cmake .. && cmake --build . && ctest
./bin/battleship
./bin/battleship -c configs/classic.cfg --seed=5
./bin/battleship --games=1000 --delay=0 --log=none
```

Параметры: `size` (8–16), `touch`, `again`, `max_moves`, `delay`, `games`, `seed`, `a` и `b` (random, hunt или human), `log`. Параметры можно задать в файле (`-c`) и в командной строке (`--ключ=значение`).

Коды завершения: 0 — бой закончен, 1 — плохие параметры, 2 — не открылся файл настроек, 3 — не расставился флот, 4 — нарушение правил, 130/143 — SIGINT/SIGTERM. По сигналу потоки игроков корректно останавливаются, печатается итог и закрывается журнал. Сигналы обрабатывает только судья (в потоках игроков они заблокированы). Стратегия `human` (ход вводит человек, например B5, q — выход) работает и в потоке: ввод читается через `poll()` с таймаутом 100 мс и `read(0)`, поэтому поток замечает остановку по Ctrl+C даже при ожидании ввода.

## 6. Результаты

```
Ход   1. Нельсон(hunt) -> G9  мимо
...
Победил Нельсон(hunt) за 110 ходов
Нельсон(hunt) выстрелов  60, попаданий  20 (33%), убито кораблей 10
Ушаков(random) выстрелов  50, попаданий  10 (20%), убито кораблей 2
```

Результат с seed=5 совпадает с однопоточной версией из ДЗ № 1, значит многопоточность не изменила логику. Серия из 1000 боёв (hunt против random, 10×10): hunt выиграл 978, в среднем 105 ходов.

## 7. Тесты и проверка

`tests/run_tests.sh` (36 проверок, включая ввод человека и Ctrl+C во время ожидания ввода) и 1692 модульных проверки на C — все проходят (`ctest`). Сборка с `-fsanitize=thread` (гонки) и `-fsanitize=address,undefined`: замечаний нет. Одно замечание ThreadSanitizer нашлось в ходе работы: флаг `over` был обычным `int`, его заменили на `_Atomic int`.

## 8. Размер программы и изменения относительно ДЗ № 1

Код программы (`src`): 571 строка (было 538; main.c 88, judge.c 218, board.c 83, player.c 121, game.h 61), тесты — ещё около 178 строк. Комментариев в коде нет. Новый код — около 90 строк: потоки и семафоры в judge.c, мьютекс вывода, ожидание ввода через `poll()` в player.c, подключение pthread в CMake. Логика поля, стратегий и разбора параметров не менялась.
