# Отчёт по индивидуальному заданию № 3

Разработка программы с использованием взаимодействующих процессов («Архитектура компьютера и операционные системы»)

## 1. Автор

Хингелов Глеб Владимирович, группа БПИ252.

## 2. Вариант и условие

Морской бой двух игроков под управлением судьи. Игроки размещают флоты на отдельных прямоугольных полях и по очереди стреляют. Судья сообщает промах, попадание или уничтожение корабля. Расположение непроверенных кораблей противнику не сообщается. Бой заканчивается уничтожением флота либо достижением лимита ходов; по лимиту объявляется ничья. Номер варианта в переданном условии не указан.

## 3. Сценарий: сущности и процессы

| Сущность | Реализация |
|---|---|
| Судья | основной процесс: расставляет флоты, передаёт ход, проверяет выстрел, выводит результат |
| Игрок 0 | отдельный процесс: выбирает клетку и запоминает ответ |
| Игрок 1 | отдельный процесс с тем же поведением |
| Поле, корабль | структуры данных судьи, отдельного поведения нет |

Итого три процесса. В отличие от ДЗ № 2, pthread больше не используется. Поля находятся в памяти судьи. Разделяемая память содержит настройки, координаты выстрела, ответ и признак завершения; скрытого расположения флотов в ней нет. Состояние стратегии каждого игрока хранится в его собственной памяти.

На игрока выделено три семафора:

```
судья:  post(turn) -> wait(shot) -> применить выстрел -> post(reply)
игрок:  wait(turn) -> выбрать клетку -> post(shot) -> wait(reply) -> запомнить ответ
```

Первое сообщение через `shot` означает готовность игрока. Семафоры обеспечивают порядок доступа к координатам и ответу. Вывод событий и запись журнала выполняет судья, поэтому мьютекс вывода больше не нужен.

Реализованы три варианта на общей игровой логике:

| Режим | Запуск | Обмен и синхронизация |
|---|---|---|
| `unnamed` (4–5 баллов) | судья создаёт двух игроков через `fork` | POSIX shared memory, неименованные семафоры `sem_init(..., 1, 0)` внутри неё |
| `named` (6 баллов) | судья создаёт двух игроков через `fork` | POSIX shared memory и именованные семафоры `sem_open` |
| `judge` / `player` (7–8 баллов) | три независимых запуска программы | POSIX shared memory и именованные семафоры с общим именем сеанса |

Для разделяемой памяти используются `shm_open`, `ftruncate`, `mmap`. Имена ресурсов содержат PID судьи либо имя независимого сеанса. Уже занятое имя не перезаписывается. В независимом режиме файловая блокировка запрещает подключение двух процессов на место одного игрока.

## 4. Пользовательский интерфейс и параметры

Консольный интерфейс показывает подготовку полей, активного игрока, номер хода, координаты, результат и смену игрока. После каждого выстрела выводятся оба поля: `.` — непроверенная клетка, `o` — промах, `X` — поражённая палуба. Непроверенные корабли не раскрываются. В конце выводятся результат и статистика. Сообщения судьи сохраняются в `battleship.log`; `--log=none` отключает журнал. Ввод-вывод реализован через файловые дескрипторы: `open`, `read`, `dprintf`, `vdprintf`, `close`.

Настройки читаются из файла (`-c`) и аргументов `--ключ=значение` в порядке их перечисления.

| Параметр | Значение |
|---|---|
| `size`, `width`, `height` | квадратное поле либо отдельные размеры, 1–16 |
| `fleet` | длины кораблей через запятую, максимум 16 кораблей |
| `touch` | 0 — запрещены касания сторонами и углами, 1 — разрешены без перекрытия |
| `placement` | `random` — случайная расстановка; `ordered` — последовательный перебор позиций |
| `a`, `b` | `random`, `hunt` или `human` |
| `again` | 1 — после попадания игрок стреляет ещё раз, 0 — ход переходит |
| `repeat` | 0 — повтор запрещён с запросом другой клетки; 1 — повтор отнимает ход |
| `first` | начальный игрок: 0 или 1 |
| `max_moves` | лимит выстрелов, 0 — без ограничения |
| `seed` | начальное значение генератора |
| `delay` | задержка между ходами в миллисекундах |
| `games` | число последовательных боёв; для независимого режима и `human` — только 1 |
| `log` | путь журнала либо `none` |

По умолчанию поле 10×10, стандартный флот `4,3,3,2,2,2,1,1,1,1`, касания запрещены, расстановка случайная, игрок 0 использует `hunt`, игрок 1 — `random`. Первым ходит игрок 0, попадание сохраняет ход, повторы запрещены.

`hunt` добивает корабль рядом с известными попаданиями, затем выбирает непроверенные клетки в шахматном порядке. `human` читает координаты вида `B5`; `q` завершает бой. Боты повторно проверенные клетки не выбирают. Подбор расстановки ограничен числом попыток: если выбранный способ не разместил флот, программа сообщает ошибку вместо бесконечного поиска.

## 5. Сборка, запуск и завершение

Среда: Linux, GCC, CMake. Команды из каталога `bs`:

```sh
cmake -S . -B build
cmake --build build
./bin/battleship unnamed -c configs/classic.cfg --seed=5 --delay=0
./bin/battleship named -c configs/classic.cfg --seed=5 --delay=0
./bin/battleship named -c configs/rectangle.cfg
./bin/battleship unnamed --a=human --repeat=1
```

Без указания режима используется `unnamed`. Для независимого запуска открыть три терминала в каталоге `bs`. Сначала запустить судью и дождаться сообщения об ожидании игроков:

```sh
./bin/battleship judge demo --seed=5 --delay=0
```

Во втором и третьем терминалах:

```sh
./bin/battleship player demo 0
./bin/battleship player demo 1
```

Настройки передаются судье; игроки получают их из разделяемой памяти. Имена сеансов состоят из латинских букв, цифр, `_` и `-`, не более 40 символов.

При завершении судья устанавливает общий признак остановки и будит игроков. В режимах с `fork` он ожидает дочерние процессы через `waitpid`. Затем уничтожает неименованные семафоры либо закрывает и удаляет именованные, отключает отображение памяти и вызывает `shm_unlink`. Независимые игроки закрывают свои дескрипторы и отображения. Удаление имён не мешает им завершить работу с уже открытыми объектами.

Обработчики SIGINT/SIGTERM устанавливают флаг остановки. Ожидание семафора выполняется с таймаутом, ввод человека — через `poll`, поэтому остановка замечается и при ожидании. Если сигнал получил отдельный игрок, он сообщает об остановке судье через SIGTERM. Принудительный SIGKILL обработать и гарантированно очистить после него ресурсы невозможно.

Коды завершения: 0 — обычное завершение, 1 — неверные параметры, 2 — ошибка файла или IPC, 3 — не удалось расставить флот, 4 — нарушение состояния игры, 130/143 — SIGINT/SIGTERM.

## 6. Результаты проверки

Сборка и запуски выполнены в Ubuntu под WSL. Во всех трёх режимах при `seed=5`, стандартных настройках и `delay=0` получен одинаковый результат:

```
Победил игрок 0 за 110 ходов
Игрок 0: выстрелов 60, попаданий 20, уничтожено 10
Игрок 1: выстрелов 50, попаданий 10, уничтожено 2
```

Для поля 6×4, флота `3,2,1`, последовательной расстановки, первого игрока 1 и лимита 4:

```
Лимит 4 ходов: ничья
Игрок 0: выстрелов 2, попаданий 1, уничтожено 0
Игрок 1: выстрелов 2, попаданий 1, уничтожено 0
```

Проверены остановка SIGINT при ожидании ввода человека и при ожидании независимых игроков: код 130, зависших процессов нет. После завершения проверенных запусков в `/dev/shm` не осталось объектов программы. Отдельный тестовый фреймворк не добавлялся.

## 7. Объём и изменения относительно ДЗ № 2

Исходники: 641 строка (main.c — 142, judge.c — 226, board.c — 83, player.c — 123, game.h — 67). В предыдущем проекте было около 571 строки.

Основное изменение — процессы, разделяемая память и три варианта работы с семафорами вместо потоков. Сохранены разбиение по файлам, стратегии, генератор, формат настроек и журнал. Добавлены прямоугольные поля, состав флота, последовательная расстановка, выбор первого игрока и режим повторного выстрела. Проверка выстрела меняет только выбранную клетку; повтор не увеличивает число попаданий, корабль уничтожается только после поражения всех палуб.
